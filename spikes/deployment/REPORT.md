## Method notes

- Kernel facilities Deno cannot call directly (Landlock) run in a child process through `libc` syscalls; the child reports through `write(2)` after `landlock_restrict_self`, so the runtime's descriptor bookkeeping cannot mask the result.
- `PTRACE_ATTACH` is measured with `strace -p` from a sibling, controlled with `strace -f` on an own child, and corroborated by `/proc/<pid>/mem` so one tool quirk cannot decide the finding.
- `SO_PEERCRED` is read by a Perl server against an `nc -U` client: Deno exposes no peer-credentials API and its FFI socket path crashes this runtime.
- Hardening directives are measured twice: effective unit properties, and behaviour inside the unit. A directive counts only when the behaviour changes.
- The modelled same-UID attacker runs with Deno permissions disabled. Deno's permission flags are an inner boundary, not an OS boundary, so granting them would understate hostile same-UID code.
- Every systemd probe uses transient `--user` units and removes them; no unit file, package, or host setting is modified.

## Same-UID findings

The decisive question for `DEP-1` is what another process of the same UID can do to the broker.

| BI-04 | broker-identity     | inconclusive | kernel.yama.ptrace_scope=1; SCM_CREDENTIALS support was not exercised                                                                 |

Interpretation, limited to what was measured:

1. Process metadata (`cmdline`, `environ`, `maps`, `cgroup`) of a same-UID sibling is readable; a canary placed in the environment was visible (PR-01).
2. Memory inspection is denied by Yama (`/proc/<pid>/mem`, `PTRACE_ATTACH` on a sibling), while tracing an own child still works (PR-02, PR-03). Denial is ancestry-based and depends on `kernel.yama.ptrace_scope >= 1`.
3. Signals are delivered to a same-UID sibling, so broker and core liveness is not protected (PR-04).
4. A credential file held open by the modelled broker was read through `/proc/<pid>/fd/<n>` by a same-UID sibling (PR-05). This is the strongest single finding: pure user-space cannot protect broker secrets, even with Yama enabled.
5. A 0600 file in a 0700 directory is readable by the same UID (SC-01); a 0444 audit file can be truncated and unlinked by its owner's UID (SC-03).
6. Unix socket credentials report only pid/uid/gid; a same-UID client is indistinguishable from the frozen core (BI-01).
7. Supplementary group `docker` plus `/var/run/docker.sock` is root-equivalent on this host (SC-04).

## Broker identity recommendation

**Variant D.** Hybrid: core, agents, and the UI stay under the deployment user; the broker and the sandbox supervisor run as dedicated system users in system units.

Rationale:

- Pure user-space cannot protect broker secrets: same-UID code read an open credential descriptor and 0600 files, and signalled sibling processes (conventional: LM-01, LM-02, LM-03, LM-04, RC-01, PR-01, PR-04, PR-05, SD-04, SD-10, RC-02, SC-01, SC-03, BI-01).
- The user manager is controllable by the deployment UID, so hard ceilings, restart discipline, and the watchdog are conventional rather than kernel-enforced for a pure user-space arm (SD-10, LM-01).
- Kernel-enforced pieces that remain available to the user-space core are Landlock filesystem and TCP rules, Yama-scoped memory denial, cgroup ceilings inside a unit, and loopback-only binding.
- Dedicated-UID enforcement claims could not be exercised from an unprivileged run (PR-01, PR-02, PR-03, PR-04, PR-05, LL-02, LL-03, NW-01, SC-01, SC-03, BI-01, BI-02, BI-03), so they are recorded as unverified rather than assumed.

Required conditions:

- Create kanbei-broker and kanbei-sandbox system users and run both as system units; the deployment user must not be able to signal, trace, or reconfigure them.
- Keep broker credentials outside ~/.local/state/kanbei and outside any path writable by the deployment user; the broker UID alone must be able to read them.
- Bind the UI to 127.0.0.1 and expose it only through the existing tunnel/Access convention; a wildcard bind was measured as externally reachable (NW-02).
- Apply Landlock filesystem and TCP rules in the sandbox supervisor before exec, and keep kernel.yama.ptrace_scope >= 1; both were measured as effective only when present.
- Verify effective systemd hardening at startup and refuse to start when a directive is accepted but ineffective (SD-04).
- Set LimitCORE=0 on broker units: core dumps are piped to the system coredump handler on this host (SC-05).
- Remove the deployment user from the docker group: membership is root-equivalent and would erase any UID separation on this host (SC-04).
- Use system units for the watchdog and alerting; a user unit is journal-only and dies with the session unless linger is enabled (RC-03).
- Kill the whole control group on supervisor termination so orphaned sandboxes cannot survive (RC-02).

Rejected alternatives:

- A/B pure user-space (home-manager or NixOS-plane user unit): measured secret isolation is none; same-UID code reads broker-held credentials and rewrites ceilings.
- C all-dedicated system units: strongest identity separation but makes mutable code and activation human-root-only, which contradicts the user-controlled mutable layer of D-2.

## Residuals

- PrivateUsers=yes started without changing the UID mapping
- process metadata is world-readable within a UID; no secret may live in argv or environ
- protection is provided by Yama; verify the sysctl remains >= 1
- denial is ancestry-based; an agent that is an ancestor of the broker could attach
- pure user-space cannot protect secrets a broker keeps open; closing descriptors immediately only shortens the window
- the ruleset only binds processes that call landlock_restrict_self; the sandbox supervisor must do so before exec
- Landlock restricts bind/connect but not UDP; UDP egress remains an accepted residual
- io_uring is enabled; io_uring operations are known to bypass parts of Landlock and seccomp, so a supervisor must add its own syscall filter
- a user manager is a per-user trust domain; any same-UID process can talk to it
- the write fails closed (EROFS) but the directive is ineffective in this user-manager configuration; a deployment that relies on it will not start, and must refuse to start rather than run with in-memory state
- the unit's loopback is a different device than the host loopback, so host 127.0.0.1 services are unreachable
- rejection is at unit start; a directive that is valid but ineffective (SD-04) is not caught this way
- with Delegate=yes the user manager owns the cgroup subtree, so hard ceilings and the watchdog are conventional under pure user-space
- the ceiling is enforced by the kernel cgroup, but a same-UID process can rewrite it (see SD-10)
- MemoryHigh throttles (reclaim pressure) rather than terminating; MemoryMax is the terminating ceiling
- a same-UID process can raise TasksMax on its own cgroup subtree (see SD-10)
- CPU quota is enforced by the kernel; same-UID code can raise it (see SD-10)
- restart discipline works, but the same UID can stop, disable, or reconfigure the unit (SD-10)
- killing a supervisor leaves orphans; a system-unit KillMode=control-group or a reaper is required
- the user manager stops at logout, so an always-on deployment dies with the session; enabling linger requires a privileged change
- an interrupted non-idempotent effect must be recorded as outcome_unknown and never retried blindly
- post-reboot recovery of the ledger writer, watchdog, and sandbox reaping remains unverified
- writer recovery and restore verification must be exercised in the ledger/backup tasks
- D-6 holds only while every listener binds 127.0.0.1 explicitly; a wildcard bind is reachable
- a wildcard bind exposes the service to the host network; the UI and broker sockets must never bind 0.0.0.0
- other host services listen on wildcard addresses; Kanbei must not add to that set and Access policy is the only ingress control
- file modes separate UIDs, not processes of one UID; secrets must be unreachable from the agent UID, not merely 0600
- append-only audit is conventional, not kernel-enforced, under one UID; an agent can erase evidence of its own denied attempt
- membership in the container-runtime group is root-equivalent; the deployment user must not hold it or every UID separation on this host is bypassable
- core dumps are piped to the system coredump handler; a broker crash could capture credential bytes, so the broker unit needs LimitCORE=0
- socket credentials identify a UID, not a component; a same-UID agent is indistinguishable from the frozen core at the kernel level
- the 0600 socket mode was measured (BI-01) but its cross-UID effect could not be exercised on this host
- the dedicated-UID arm cannot be exercised from this unprivileged run; its enforcement is unverified, not assumed
- message-level SCM_CREDENTIALS must be exercised by the broker task, not assumed from socket credentials
- the pure user-space posture is admissible only with the accepted residuals recorded; it is not a claim of kernel-enforced secret isolation
- an unwritable audit sink denies the effect and records the denial; no effect runs unrecorded
- Dedicated-UID enforcement is unverified on this host because no privileged operation was permitted; the decision relies on the kernel UID model plus review.
- If a future host allows the deployment user to join docker or equivalent groups, all UID separation is void.
- Yama ptrace scope, Landlock ABI, and cgroup delegation are host configuration; a host rebuild can silently weaken them unless startup verification checks effective values.
- UDP egress, io_uring, and SCM_CREDENTIALS behaviour remain outside the measured enforcement.
